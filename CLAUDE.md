# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This repository is a single self-contained HTML file: `Markdown-Editor.html` (~11.6MB — see Dependencies below for why). It is a client-side, no-build "Markdown Studio" editor with live preview, multi-tab documents, undo/redo, search & replace, theming, a draggable synced-scroll split view, focus modes (hide editor or preview), fullscreen mode (with a CSS fallback for iOS Safari), a table of contents panel, table row/column controls, image paste/drop, an embedded Excalidraw drawing tool, an SVG-icon toolbar, document templates, HTML export, copy-formatted-note-to-clipboard, print, responsive layout for narrow viewports, an installable app icon/manifest, and local file save/load. There is no package manager, build step, linter, or test suite — the entire application (markup, CSS, and JS) lives in this one file.

## Running / developing

There is no build or dev server. To work on the app, open `Markdown-Editor.html` directly in a browser (double-click, or `open Markdown-Editor.html` on macOS). Reload the browser tab after every edit to see changes — there is no hot reload. The file is fully standalone (no network access required, works from `file://`) — see Dependencies below.

There are no automated tests. Verify changes manually in the browser: type in the editor pane and confirm the preview pane, toolbar buttons, and keyboard shortcuts behave as expected.

## Dependencies (bundled, not CDN)

`marked` and `highlight.js` are inlined verbatim as `<script>` blocks in `<head>` (not loaded from a CDN) so the app has zero external requests and works fully offline. If either library needs a version bump, download the new minified build and replace the corresponding inline `<script>` block's contents — do not reintroduce `<script src="https://...">` CDN tags. When editing near these blocks, be careful with tooling that matches on line content: they're ~40K–120K characters of minified code on effectively single long lines.

A third, much larger bundle — the full Excalidraw drawing app (`excalidraw.html`, a ~8.5MB standalone Vite build, custom-titled "Kritzelbuch") — is embedded the same way but **base64-encoded** rather than raw, inside `<script type="text/plain" id="excalidrawSource">`. Raw embedding wasn't viable here: unlike `marked`/`highlight.js` (pure JS, no markup), `excalidraw.html` is itself a full HTML document containing real `</script>` tags, which would prematurely close a wrapping `<script>` element. Base64 sidesteps that entirely (its alphabet contains no `<`, `>`, `/`, quotes, or backticks) at the cost of ~33% size inflation. See the "Drawing (Excalidraw)" section below for how this is decoded and used, and if this is ever rebuilt/updated, regenerate it the same way — read the new `excalidraw.html`'s raw bytes, base64-encode them, and replace only the text between the `<script id="excalidrawSource">` tags.

The `Icons/` folder (a set of individually-downloaded SVGs from svgrepo.com, one per toolbar button plus one larger "app icon" illustration) is a source folder, not something the running app reads at runtime — every icon used by the app is inlined directly into `Markdown-Editor.html` at edit time, same "no external file requests" rule as everything else. Two different treatments depending on use:
- **Toolbar icons** (header actions, formatting toolbar, table controls — see "Conventions to preserve" below) are inlined as raw `<svg>` markup in place of the emoji they replaced. Each source SVG is normalized before inlining: strip the `width`/`height="800px"` attributes (sizing comes from CSS, see `.icon-btn svg`/`.fmt-btn svg`/`.toolbar-btn svg`), and rewrite any hardcoded `fill`/`stroke` hex color (including ones hidden inside an inline `<style>.st0{fill:#000000}</style>` block, as two of the source files had) to `currentColor` so the icon inherits the button's text color and keeps working across hover/active states and themes without a second copy. None of the 39 toolbar icons contain `<defs>`/`clipPath`/gradients, so inlining many of them into one document has no ID-collision risk — re-check this if a newly added icon does use those.
- **The app icon** (`Icons/Software Icon_editor-software-text-svgrepo-com.svg`) is instead rasterized to PNG at a few fixed sizes (32/180/192/512px) and embedded as `data:image/png;base64,...` in `<link rel="icon">`/`<link rel="apple-touch-icon">`/the inline web manifest (see "App icon & manifest" below) — an favicon/apple-touch-icon can't be a live inline `<svg>`, and rasterizing keeps it a static, cacheable size instead of Chrome/Safari doing it repeatedly. The apple-touch-icon and manifest icons are flattened onto an opaque white background before encoding (iOS fills transparent apple-touch-icon pixels black otherwise); the plain favicon keeps its transparency since browser tab icons handle that fine. macOS's `qlmanage -t -s <px> -o <dir> <file>.svg` (Quick Look's thumbnailer, invoked from the shell) is what rasterizes the SVG — there's no `rsvg-convert`/ImageMagick dependency here, `qlmanage` renders it correctly via WebKit and needs no extra install on a Mac.

## Architecture

Everything is in one file with three sections: `<style>` (CSS custom properties driving both the app chrome and the swappable preview themes), static `<body>` markup for the header/toolbar/tab bar/split-pane layout, and a single `<script>` block with all application logic. There are no modules — every function is a global in that script block.

### Tab / document model
- `tabs` is the in-memory array of open documents; each tab is `{ id, name, content, fileHandle, isModified, history, historyIndex }`.
- `activeTabId` tracks the current tab. `getCurrentTab()` looks it up.
- The `<textarea id="markdownInput">` and preview `<div>` are singletons shared by all tabs — switching tabs (`switchTab()`) writes the outgoing tab's content back into the tab object before swapping in the new tab's content into the shared editor/preview elements. Any new feature that reads/writes "the current document" must go through this same save-on-switch pattern or it will leak state between tabs.
- `fileHandle` holds a File System Access API handle (when the browser supports `showSaveFilePicker`) so `saveCurrentFile()` can write back to the original file without a picker; falls back to a download-blob `<a>` click otherwise.
- `tab.isDefaultName` tracks whether a tab still has its auto-generated name (`true` for a blank "Neu" tab, `false` for anything opened from a file). While `true`, `updateTabNameFromFirstHeading()` (called from `updatePreview()`) live-renames the tab from the document's first line whenever it's a `#`–`######` heading, sanitized into a filename. `saveCurrentFileAs()` sets it back to `false` on success either way (native picker or download fallback) so a name the user actually chose is never silently overwritten again. Persisted per-tab so this doesn't reset on reload.

### Undo/redo
- Per-tab history is a plain array of full-content snapshots (`tab.history` / `tab.historyIndex`), capped at 80 entries. `recordHistory()` is debounced 400ms after typing (see the `editor.addEventListener('input', ...)` handler) so keystrokes coalesce into one snapshot; explicit actions (toolbar formatting, task-checkbox toggles, replace-all) call `recordHistory()` immediately instead.

### Formatting toolbar — toggle-aware, not just insert
`insertFormatting(type)` is deliberately not a naive "insert markdown syntax" function:
- Inline styles (bold/italic/strike/code) go through `applyInlineFormat()`, which detects whether the current selection (or the text immediately surrounding the cursor) is already wrapped in that syntax and un-wraps it instead of double-wrapping — this is what makes the toolbar buttons behave as toggles.
- Block/line-prefix styles (h1–h6/ul/ol/task/quote) operate per-line over the full selection: `prefixCleanupRegex` strips any existing prefix before applying the new one, so switching a line from `# ` to `> ` doesn't leave both prefixes stacked. Preserve this "detect current type → strip → reapply" pattern when extending formatting types, rather than blindly prepending syntax. Headings are a single `<select id="headingSelect">` (h1–h6), not six separate buttons — its `onchange` calls `insertFormatting(this.value)` then immediately resets `selectedIndex` back to the placeholder, since the select itself isn't meant to hold state (see active-format indicator below for what shows the *current* heading level).
- The Enter-key handler (in the `keydown` listener) implements smart list continuation (task/numbered/bullet) independently of `insertFormatting`, including auto-incrementing numbered lists and exiting a list when Enter is pressed on an empty list item. Keep this logic in sync if list-prefix formats change.
- `Tab`/`Shift+Tab` inside the editor are intercepted in the same `keydown` listener to indent/outdent (2 spaces) rather than moving focus out of the textarea — a collapsed cursor inserts/removes 2 spaces directly, a range selection goes through `indentLines('indent' | 'outdent')`, which is line-based like the block-prefix logic above (same toolbar buttons: ⇤/⇥).
- Every formatting insertion is empty-by-default (no "Listenpunkt"/"Zitat"/"fetter Text"-style filler): an empty selection produces just the bare syntax (`**` `**`, `> `, `[]()`, an empty `| | |` table skeleton, …) with the cursor placed where typing should start. Preserve this if extending `insertFormatting`/`applyInlineFormat` — don't reintroduce placeholder words "to show what it looks like."

### Active-format indicator
`updateFormatButtonStates()` (called from `updatePreview()` and from a `document`-level `selectionchange` listener gated on `document.activeElement === editor`) highlights which toolbar controls apply at the current cursor position: `detectBlockTypeAtLine()` reuses the same line-prefix regexes as `insertFormatting` to set the heading `<select>`'s value or toggle the ul/ol/task/quote buttons' `active` class; `detectInlineFormatsAtCursor()` scans the current line for bold/italic/strike/code spans and checks whether the cursor position falls inside a match. This is a heuristic line-local regex scan, not a real markdown parser — good enough for a toolbar hint, but don't expect it to handle pathological nesting/escaping correctly.

### Preview rendering
`updatePreview()` re-parses the entire editor content through `marked.parse()` on every input event (no incremental diffing). Task-list checkboxes in the rendered preview are made interactive by `attachTaskCheckboxListeners()`, which re-binds a `change` listener to every checkbox after each re-render; toggling one calls `toggleTaskInMarkdown()`, which finds the Nth checkbox pattern in the raw markdown via regex and flips `[ ]`/`[x]` — this only works because checkbox order in the rendered DOM matches checkbox order in the source text, so any change to list rendering must preserve that ordering guarantee.

### Custom `marked.Renderer()` (`hljsRenderer`) — code highlighting, images, task list bullets
A single `hljsRenderer` instance overrides three default methods; if `marked` is ever upgraded, re-check all three against the installed version's `Renderer.prototype` since they replicate (not just extend) marked's default behavior and rely on its exact method signatures (object-destructured args like `{ text, lang }`, not positional):
- **`code({ text, lang })`** — `marked` v5+ removed the old synchronous `highlight` callback in `marked.setOptions()`; passing it is silently ignored (no error, code blocks just render unhighlighted — this was actually broken for a while before being noticed and fixed). Calls `hljs.highlight()`/`hljs.highlightAuto()` and returns `<pre><code class="hljs ...">`.
- **`image({ href, title, text })`** — resolves `asset:ID` hrefs to the real data URI (see the image-asset-map section below); everything else passes through unchanged.
- **`listitem(item)`** — marked's default renderer never adds any class to task-list `<li>` elements, and whether the checkbox ends up a direct child of `<li>` or nested inside a `<p>` depends on whether the surrounding list is "loose" (any blank line between items in that list makes the *whole* list loose, even items with no blank line adjacent to them) — so a CSS selector like `li:has(> input[type=checkbox])` only catches the tight case. This override replicates marked's default task-checkbox logic exactly but additionally tags the `<li>` with `class="task-list-item"` regardless of looseness, which `.markdown-body li.task-list-item { list-style-type: none; }` uses to suppress the bullet (GitHub renders task items without a bullet marker; showing both a bullet *and* a checkbox reads as broken/unfamiliar). Keep the CSS rule and this renderer override in sync in both the live preview stylesheet and the `exportAsHtml()` template string.

### Editor/preview pane visibility (split view, focus modes)
`showEditor` and `showPreview` are independent booleans; `applyPaneVisibility()` is the single function that reconciles both into the `editor-hidden`/`preview-hidden` classes on `#mainContainer`, the two toggle buttons' `active` state, and the formatting toolbar's visibility. `toggleEditor()`/`togglePreview()` both guard against hiding both panes at once (auto-re-enables the other one) — any new code that flips these flags directly should go through `applyPaneVisibility()` afterward rather than touching classes ad hoc. The CSS grid (`main { grid-template-columns: var(--split-ratio, 50%) 6px 1fr }`) is now **three** tracks, not two — the middle one is `#paneResizer` (see "Split-pane resizing" below) — and relies on `.editor-pane`/`.pane-resizer`/`.preview-pane` each having an explicit `grid-column: 1`/`2`/`3` (columns) or `grid-row` (mobile, see Responsive layout below). Without those pins, hiding a grid item via `display: none` makes the browser auto-place the remaining items back into earlier tracks instead of stretching them, collapsing the layout. Keep all three pins in sync if this grid is touched — `main.editor-hidden`/`main.preview-hidden` zero out both the hidden pane's track *and* the resizer's track (`0 0 1fr` / `1fr 0 0`) so the resizer disappears along with the pane it would otherwise sit next to.

### Split-pane resizing
`#paneResizer` is a 6px `<div>` between `.editor-pane` and `.preview-pane` in the grid (see above); dragging it updates `splitRatio` (a percentage, 0–100, clamped to 15–85) and writes it to the `--split-ratio` CSS custom property via `applySplitRatio()`, which both the desktop (`grid-template-columns`) and mobile (`grid-template-rows`, see Responsive layout) grid definitions read — so one JS-side value drives both axes and the layout re-flows for free on window resize since it's percentage-based, not pixel-based. Dragging is implemented with Pointer Events (`pointerdown`/`pointermove`/`pointerup` + `setPointerCapture`) rather than mouse events specifically so it works uniformly for mouse, touch, and pen without separate touch handlers. Which axis a drag affects is decided *at `pointerdown` time* by checking `window.matchMedia('(max-width: 640px)')` — the same breakpoint the responsive layout media query uses — not by anything CSS-computed, since there's no direct way to ask the grid "which axis is active" from JS. `splitRatio` is persisted like any other setting (see Persistence) and reapplied via `applySplitRatio()` on load; the resizer itself is hidden via the same `editor-hidden`/`preview-hidden` classes `applyPaneVisibility()` already toggles (see above) rather than a separate visibility code path.

### Fullscreen mode
`toggleFullscreen()` first feature-detects `document.documentElement.requestFullscreen && document.fullscreenEnabled`. Where supported, it's just the standard `requestFullscreen()`/`exitFullscreen()`; a `fullscreenchange` listener (not the button's own click handler) syncs the button's `active` class, since fullscreen can also be exited via `Esc` or browser UI outside the app's control. Note for testing: some sandboxed/automated browser contexts reject `requestFullscreen()` with `"Permissions check failed"` even though the API and `document.fullscreenEnabled` both report as available — that's an environment restriction, not a sign the code is wrong.

Where unsupported — notably iOS Safari, which has never implemented the Fullscreen API for regular elements (only `<video>` via `webkitEnterFullscreen`) — calling `requestFullscreen()` would throw a **synchronous** `TypeError` before any promise even exists, so the old code's `.catch()` never ran and the button silently did nothing. The fallback instead toggles a `body.pseudo-fullscreen` class (`position: fixed; inset: 0; height: 100dvh; z-index: 9999`) to fill the viewport with CSS alone; the button's `active` class is toggled directly in this branch since there's no `fullscreenchange` event to listen for. This CSS fallback only fills whatever viewport Safari currently shows (its own chrome stays) — the actual "real fullscreen on iPhone" experience comes from the app icon/manifest work (below): once added to the Home Screen via `apple-mobile-web-app-capable`, the app launches with zero Safari chrome at all.

### App icon & manifest
`<head>` carries a 32×32 favicon, a 180×180 `apple-touch-icon`, and a web manifest (`name`/`icons`/`display: "standalone"`/theme colors) — all three as `data:` URIs, all generated from `Icons/Software Icon_editor-software-text-svgrepo-com.svg` (see Dependencies above for how). `apple-mobile-web-app-capable`/`apple-mobile-web-app-title`/`theme-color` meta tags are what make "Add to Home Screen" on iOS launch the app standalone (no Safari chrome) instead of as a bookmarked tab — this is the real fix for "fullscreen on iPhone", complementing the in-page CSS fallback above. If the app icon SVG is ever swapped, regenerate all four embedded images (favicon/apple-touch-icon/manifest's 192px/manifest's 512px) together so they stay visually consistent — there's no build step to do this automatically.

### Table of contents
A floating button (`#tocToggleBtn`) and panel (`#tocPanel`) positioned `position: absolute` inside `#mainContainer` (not inside `.preview-pane`) specifically so they stay put on screen while the preview scrolls underneath — `.preview-pane` is the scroll container, so anything absolutely positioned *inside* it would scroll away with the content. `updateTocPanel()` rebuilds the list from `preview.querySelectorAll('h1, h2, h3, h4, h5, h6')` (only when the panel is open — cheap to call unconditionally from `updatePreview()`) and each entry calls `headingEl.scrollIntoView()` directly rather than generating anchor IDs/slugs, since the actual heading elements are already right there in the live DOM. Closes on: entry click, outside click, `Escape` (added to the same shared listener as the other modals), and is force-hidden via CSS whenever `.preview-hidden` is active (no preview to outline).

### Table controls
A contextual bar (`#tableControls`, between the formatting toolbar and `<main>`) that only appears while the cursor sits inside a markdown table, driven by `findTableBlock()` — it locates the contiguous run of "lines containing a pipe" around the cursor and confirms the second line matches `TABLE_SEPARATOR_RE`, so a stray `|` in a sentence never gets misdetected as a table. This is a from-scratch line-based table editor operating on raw text, not the rendered DOM:
- `getCellRanges(lineText)` finds cell character ranges by locating unescaped `|` positions and adding virtual boundaries at the string ends when a row omits the leading/trailing pipe (both are valid GFM) — this is what lets column-detection work identically for `| A | B |` and bare `A | B` styles.
- Row insert/delete and column insert/delete all funnel through `commitTableEdit()`. Column operations rebuild **every** row in the block via `buildRowFromCells()` into a canonical `| a | b |` shape — this normalizes/reformats the whole table (loses any hand-aligned padding) but sidesteps a much harder problem (splicing a new cell into arbitrarily-padded existing rows). Accepted trade-off; don't try to preserve exact original spacing without a good reason to.
- Row insert/delete on the header or separator line is deliberately redirected/blocked (`cursorLine <= separatorLine` guard) — the separator **must** immediately follow the header for GFM to recognize the table at all, so "insert a row before the header" can't mean what it literally says without breaking the table; it's redirected to insert as the first body row instead. Deleting the header/separator via this UI is blocked outright.
- The bar's visibility (`updateTableControlsVisibility()`) is gated on `showEditor` in addition to cursor-in-table — it's called both reactively (`selectionchange`, `updatePreview()`) and explicitly from `applyPaneVisibility()`, because otherwise toggling the editor pane hidden wouldn't hide a bar that's logically about editing raw source you can no longer see.

### Synchronized scrolling
`syncScrollFrom('editor' | 'preview')` mirrors scroll position by percentage (`scrollTop / (scrollHeight - clientHeight)`) between the textarea and `#previewPane`. The `isSyncingScroll` flag plus a `requestAnimationFrame` reset prevents the two scroll listeners from re-triggering each other in an infinite loop — keep both the flag and the rAF-deferred reset if this is touched (a synchronous reset re-enters before the mirrored scroll event fires and recurses). Disabled automatically whenever either pane is hidden (nothing to sync against) and toggleable via `syncScrollBtn`/`syncScrollEnabled`.

### Image insertion (paste, drag-and-drop & the 🖼️ toolbar button) — asset map, not inline base64
Pasted/dropped/picked images are **not** embedded as a giant inline `data:` URI in the visible markdown source. Each tab has a `tab.assets` map (`{ img_1: 'data:image/...;base64,...', ... }` plus `tab.assetCounter`); the editor text only ever holds a short `![name](asset:img_1)` reference. This exists specifically to keep the source editable/scrollable/diffable — a multi-MB base64 line used to make the textarea (and undo history, and search) unwieldy.
- **Insert flow**: the `editor` `paste` listener, the window `drop` handler, and the formatting toolbar's 🖼️ "Bild einfügen" button (`triggerImageFileInsert()`, which just clicks the hidden `#imageFileInput` — same `<input type="file">`-behind-a-button pattern as the header's 📂 "Öffnen") all funnel into the same `requestImageInsertChoice(file)`, an async dialog (`#imageInsertModal`) that loads the image, offers "Verkleinert einfügen" (canvas-resized to `IMAGE_MAX_DIMENSION`px longest side, re-encoded as JPEG at `IMAGE_JPEG_QUALITY`, hidden if the image is already smaller) alongside "Original einfügen", and resolves a Promise with `{ dataUrl, name }` (or `null` if cancelled). `insertImageAsset(dataUrl, name)` then does the actual asset-map write + short-reference insertion, at whatever the textarea's current selection/cursor position is (unaffected by the file picker's own focus stealing — text selection state survives that). Don't reintroduce a "just insert the file directly" path that skips this dialog — that's the exact problem this system replaced.
- **Render**: `hljsRenderer.image({ href, title, text })` (the same custom `marked.Renderer()` used for syntax highlighting) resolves an `asset:ID` href to the real data URI via `getCurrentTab().assets` at render time; any other href passes through unchanged. This is why switching tabs "just works" for images — the renderer always looks at whatever tab is currently active.
- **Save / export**: `editor.value` (and therefore `tab.content`, localStorage, undo history) always contains the short `asset:` reference — never the full base64. `saveCurrentFile()`/`saveCurrentFileAs()` run the content through `inlineAssetsIntoContent(content, assets)` (regex-substitutes `asset:ID` back to the real data URI) before writing, so the saved `.md` file is still a portable, standalone document with no dependency on this app. `exportAsHtml()` doesn't need this step — it already renders through `hljsRenderer.image`, which resolves the reference at render time.
- **Opening/pasting content that already has inline base64 images** (a `.md` file saved elsewhere, or one saved by an older version of this app): `createNewTab()` runs all new tab content through `extractInlineImagesToAssets(content)`, which regex-detects `![alt](data:...;base64,...)` and converts it into the asset-map form on the way in. Any code path that sets a tab's initial content should go through `createNewTab`, not assign `tab.content` directly, or this normalization gets skipped.
- Drag-and-drop still branches on MIME type: images go through the dialog into the *current* tab's assets, everything else still opens as a new tab via `createNewTab` (the original behavior — don't collapse that branch).

### Drawing (embedded Excalidraw)
The 🖌️ "Zeichnung" toolbar button opens `#drawingModal`, whose `<iframe id="drawingFrame">` is loaded via `frame.srcdoc = getExcalidrawHtml()` (base64-decoded once, cached in `cachedExcalidrawHtml`) rather than `frame.src` pointing at a sibling file. That choice is deliberate and load-bearing: an iframe using `srcdoc` is same-origin with the embedding page **by spec, regardless of whether the parent was opened over http(s) or via `file://`**. A `src="excalidraw.html"` iframe would only reliably be same-origin over http(s) — for the "download the one file and double-click it" use case, that same-origin guarantee is what makes the rest of this section possible at all.

There is no supported API for scripting the standalone Excalidraw app from the outside (it's the full end-user app, not the `@excalidraw/excalidraw` React component library, which *does* have a clean imperative API but would mean building a whole separate app rather than reusing this file). Both directions below instead drive Excalidraw's actual UI programmatically, discovered by inspecting its DOM for stable hooks (`data-testid` attributes and element `id`s — Excalidraw's own E2E test infrastructure, far more stable across rebuilds than guessed CSS classes or coordinates) rather than by any documented contract:
- **Loading an existing drawing** (`openDrawingModal(assetId)`) polls for `canvas.excalidraw__canvas.interactive` to confirm the app has actually mounted, then simulates a native drag-and-drop of the asset's stored PNG onto that canvas via `dropFileOntoExcalidraw()`. This works because Excalidraw embeds the full editable scene inside a `tEXt` chunk of any PNG exported with "Szene einbetten" on, and *automatically* restores it when such a file is dropped onto the canvas — a real, long-standing Excalidraw feature this leans on rather than reimplements.
- **Saving** (`exportDrawingBlob()`) clicks through Excalidraw's own menu → `[data-testid="image-export-button"]` → forces `#exportEmbedSwitch` (embed scene) on and `#exportOnlySelected` off → clicks the `button[aria-label="Als PNG exportieren"]` → captures the resulting `Blob` by patching `URL.createObjectURL` **inside the iframe's own window**, not the parent's, and not by touching any Excalidraw-internal function. Forcing `#exportOnlySelected` off is not optional: it defaults to on whenever anything is or *was* selected (surviving even a subsequent deselect/Escape), and left on it silently exports only the selected shape(s) — this was an actual bug caught only by testing a two-shape drawing with the second shape left selected, not something obvious from reading the code.
- That same "Als PNG exportieren" click also triggers a **real browser download** of the PNG as a second, redundant copy — on top of, not instead of, the capture above. If the user has Chrome's "Ask where to save each file before downloading" enabled, that download is exactly what pops a native "Save As" dialog. Two earlier fix attempts targeted the wrong mechanism entirely (**File System Access API** / `showSaveFilePicker`) before this was pinned down empirically: simulating `showSaveFilePicker`'s presence and tracing the actual click sequence showed **zero calls to it** — `browser-fs-access` (which this build is written against) goes straight to its plain fallback (`URL.createObjectURL(blob)` → a `download`-attributed `<a>` → `.click()`) unconditionally for this button, never attempting FSA at all. Both `showSaveFilePicker` patches were reasoning about a code path that was never being exercised, which is also why they never fixed anything despite being individually correct about how FSA detection works (`delete`, not `= undefined`, is still the right way to remove a "supported" check based on `"x" in window` — that lesson just didn't apply here). A real native OS save panel is also invisible to a CDP/automation screenshot (it isn't part of the page's rendered DOM), so testing any of this by screenshot alone reads as "fixed" even when it isn't — every round of this had to be verified by tracing actual call sequences (patched globals recording what got called, with what arguments), not by looking at what rendered.
- The actual fix has to intercept the download itself, and a `window`/`document`-level click listener doesn't work either: instrumenting `HTMLAnchorElement.prototype.click` directly (logging `isConnected`, the `download` attribute, and the `href` on every call) proved the anchor `browser-fs-access` creates is **never attached to the document** before `.click()` is called. A detached node has no ancestor chain, so it has no path to bubble (or be intercepted in capture phase) through `window`/`document` — a listener there simply never sees it, regardless of phase. The only reliable interception point is the method itself. `openDrawingModal()` therefore patches `win.HTMLAnchorElement.prototype.click` right after the canvas mounts: calls on a `download`-attributed anchor pointing at a `blob:` URL are suppressed outright (return without calling through), everything else passes through unchanged. `exportDrawingBlob()`'s own `win.URL.createObjectURL` patch has already captured the Blob by the time this would fire, so suppressing the download loses nothing. Unlike the FSA case, this doesn't need to land before Excalidraw's module evaluates — `a.click()` is looked up on the prototype fresh every time it's called, nothing caches a reference to it at module-load time, so patching it post-mount (once, for the modal's whole session) is sufficient.
- Both are inherently coupled to *today's* Kritzelbuch/Excalidraw build's DOM structure and German menu strings. If that build is ever regenerated from a newer Excalidraw version, re-verify every selector above still resolves before assuming any of this still works — none of it is a stable, versioned contract.

**The bundled `excalidraw.html` also contains a dormant, unrelated `postMessage` autosave layer** (message types `kritzelbuch-ready`/`kritzelbuch-load`/`kritzelbuch-save`/`kritzelbuch-request-save`, a status indicator, and a German "Kein Speicherziel — Seite läuft nicht eingebettet" banner) baked into the fork at the source level by whoever built it — **this app's own JS never sends or listens for any of those messages** and still exclusively uses the drag-and-drop/export-button-click flow described above. Two things were patched directly into the compiled bundle (both `excalidraw.html` and the re-encoded base64 blob were updated together, per the regeneration steps below) because they leaked through into the UI regardless:
- The "Kein Speicherziel…" banner's render condition was hardcoded to never show (`!Q9` → `!1` in the minified source) — it was firing on every open because `window.location.origin` is the opaque string `"null"` inside a `srcdoc` iframe (see above), which the dormant layer misreads as "not embedded," even though embedding-via-srcdoc is working exactly as intended.
- Excalidraw's own native "Speichern" action (Ctrl/Cmd+S, saves an `.excalidraw` file straight to the user's disk) was disabled by passing `UIOptions:{canvasActions:{saveToActiveFile:!1}}` to the `<Excalidraw>` component in the minified source — this app only ever wants the drawing captured back into the markdown document's asset map, never written to disk as a separate file. `export` (the PNG-export menu `exportDrawingBlob()` depends on) and `loadScene` ("Öffnen") were deliberately left enabled.

If `excalidraw.html` is ever regenerated from a newer build of this fork, re-check whether these two patches still apply/are still needed before re-running the base64 regeneration step — a future build might remove the dormant autosave layer entirely, or expose a cleaner flag for either fix.

Saving writes the resulting data URL into `tab.assets[assetId]` exactly like a pasted image (new drawings go through the same counter-based `img_N` allocation as `insertImageAsset`), plus `tab.drawingAssetIds[assetId] = true` so it's distinguishable from a regular photo later. Editing an *existing* drawing reuses the same `assetId` rather than minting a new one — the markdown source's `![Zeichnung](asset:img_3)` reference never has to change, only the asset data it points to, so nothing downstream (undo history diffing, search, the reference itself) needs to know an edit happened at all.

In the rendered preview, `hljsRenderer.image` wraps only assets present in `tab.drawingAssetIds` in a `<span class="drawing-wrapper" data-asset-id="...">` with a hover-revealed "✏️ Bearbeiten" button; a single delegated click listener on `preview` (registered once, not re-bound per render) reopens `openDrawingModal` for whichever wrapper was clicked — clicking the image itself works too, since both are inside the same wrapper. This wrapping is suppressed during `exportAsHtml()` via the `suppressDrawingControls` flag (flipped on immediately around that one `marked.parse()` call) so a standalone exported HTML file gets a plain `<img>` instead of a button wired to a function (`openDrawingModal`) that won't exist in that file.

`tab.drawingAssetIds` is persisted the same way as `tab.assets`/`tab.assetCounter` and must stay in sync with them in every place tabs are created, saved, or restored (`createNewTab`, `saveStateToLocalStorage`, `loadStateFromLocalStorage`) — it was missed on the first pass through `saveStateToLocalStorage`/`loadStateFromLocalStorage` and silently dropped the "this is a drawing" marker on every reload until caught by testing the full persistence round-trip explicitly, not just the happy path of inserting a drawing once. Note this marker is inherently lost if a `.md` file is closed and reopened later (or opened on another machine) — `extractInlineImagesToAssets()` has no way to know from a bare `![alt](data:...)` that it originally came from Excalidraw, so it becomes a regular (non-editable-via-Excalidraw) image on reimport. Detecting this by peeking into the embedded PNG's own metadata would be possible but isn't implemented — an accepted limitation, not an oversight.

### Document templates
The `TEMPLATES` array (10 entries, each `{ id, name, desc, content }`) backs a picker modal (`#templateModal`, opened by `openTemplateModal()`) that both the header ✨ "Neu" button and the tab bar's `+` button open now instead of calling `createNewTab()` directly — the two buttons are the same logical action ("new document") and must stay in sync if this is touched again. Picking a card calls `selectTemplate(id)`, which sets `lastTemplateId`, closes the modal, and calls `createNewTab(null, tpl.content)` — passing `name: null` keeps `isDefaultName: true` so the existing first-heading auto-rename still applies to the new tab. `lastTemplateId` is persisted like any other setting (see Persistence) and re-highlighted (`.template-card.last-used`) the next time the picker opens, mirroring how the theme `<select>` remembers its value. The one internal caller that still creates a tab without the picker — the app-bootstrap fallback that seeds the very first "Willkommen"/`defaultContent` tab when `localStorage` is empty — deliberately keeps calling `createNewTab()` directly so first load isn't interrupted by a modal.

Note for anyone adding/editing template content: an empty markdown list marker with truly nothing after it — a bare `- ` or `1. ` as the last (or only) thing in its block, with no other list items and no trailing text — gets rendered by this version of `marked` as a literal `<p>- </p>` paragraph instead of an empty `<ul>`/`<ol>`, unlike an empty task item (`- [ ] `) which *does* render as a real checkbox (see the custom `listitem` override above). Existing templates route around this by leaving those sections' bodies genuinely blank (no dash at all) rather than a dash with nothing after it — don't reintroduce a bare trailing `-`/`1.` expecting it to render as a list.

### HTML export & print
`exportAsHtml()` builds a fully standalone HTML document (inline `<style>`, inline rendered markdown) by reading the *current* theme's `--preview-*` custom properties off `getComputedStyle(preview)` rather than hardcoding each theme's colors again — if a new preview theme is added, the export picks it up automatically as long as it still defines the same `--preview-*` variable names. It also inlines whichever of `#hljs-theme-light`/`#hljs-theme-dark` is currently active so exported code blocks keep their highlighting. Printing (and thus "Print to PDF", which is how this app's PDF export works — the 🖨️ button is just `window.print()`) uses an `@media print` block that hides everything except `.preview-pane`. That block also carries the current theme's `--preview-bg` onto `html`/`body`/`.preview-pane` and sets `print-color-adjust: exact` (plus the `-webkit-` prefix) on every element — without the latter, browsers silently drop background colors when printing by default (an ink-saving heuristic), so a themed PDF would print on a plain white page regardless of what CSS said. Keep both the background-color propagation and the color-adjust override if this block is touched, or a dark theme's PDF/print output will look unthemed again.

### Copy formatted note to clipboard
The 📋 toolbar button (`copyFormattedToClipboard()`) does not save a file — it copies the rendered document straight onto the system clipboard as a formatted (rich-text) note, so pasting into Word/Outlook/Gmail/etc. inserts headings, bold/italic, lists, tables, and inline images rather than raw markdown source. Implementation is deliberately not a hand-rolled RTF (or HTML) serializer:
- Before rendering, `editor.value` goes through `expandBlankLinesForClipboard()`, which turns each blank line *beyond* the first in a run into a literal `&nbsp;`-only paragraph. Markdown normally collapses any number of consecutive blank lines into a single block separator, so without this step there'd be no way for a user to add deliberate extra spacing (e.g. more breathing room under a heading) that survives into the copied note — this is the one place in the app where blank-line *count* is semantically meaningful rather than being pure formatting. It tracks fenced-code-block state (toggling on any \`\`\`/~~~ line) and passes lines through untouched while inside one, since a blank line there is literal code content, not a paragraph separator, and must not get injected with stray "&nbsp;" text.
- It then re-renders that expanded markdown through `marked.parse()` with `suppressDrawingControls` on (same trick `exportAsHtml()` uses) into an offscreen, off-DOM-flow clone of `#markdownPreview` (same `className`, so it picks up the active theme's computed styles), then selects that clone's contents with a `Range`/`Selection` and calls `document.execCommand('copy')`.
- Copying a live selection is what makes the browser itself walk the selected DOM and bake computed styles into the clipboard's HTML payload (and derive a plain-text fallback) — this is the same mechanism as manually selecting page content and pressing Ctrl+C, so it doesn't require authoring a second styling pass or a custom clipboard MIME type. Images are already resolved to real data URIs by `hljsRenderer.image` by the time this DOM exists, so they're copied inline with no extra asset-map lookup.
- `execCommand('copy')` is the deprecated-but-still-universally-supported API for this; it was chosen over the modern async Clipboard API (`navigator.clipboard.write`) because browsers restrict that API's `ClipboardItem` MIME types (`text/html`/`text/plain`/`image/png` only, sanitized) — a hand-authored `<style>`-block HTML document (like `exportAsHtml()` produces) is not guaranteed to render its styling when pasted into Word/Gmail, whereas a browser-serialized selection reliably inlines styles per element.
- A toast (`showToast()`, `#appToast`) confirms success/failure since there's no other visible feedback for a clipboard write.

### Modals (keyboard shortcuts help, image insert dialog, template picker)
All follow the same plain pattern: a `.modal-overlay`/`.modal-card` pair, closed via a ✕ button, a click on the overlay backdrop (checked with `event.target === this` in the inline `onclick`), or the shared document-level `Escape` listener (which closes all of them, each gated on its own `active` class). The drawing modal (see above) is the odd one out — it has extra iframe-mount logic — but still reuses the same overlay/card CSS. If another modal is added, extend this shared pattern instead of copy-pasting the overlay/backdrop-click/Escape wiring again.

### Word/character count
`updateStats()` writes `${words} Wörter · ${chars} Zeichen` into `#docStats` in the footer; it's called from inside `updatePreview()` (so it can't drift out of sync with the rendered content) and from `setEmptyState()` (to clear it).

### Theming
Ten preview themes (`theme-github-light/dark`, `solarized`, `nord`, `academic`, `dracula`, `monokai`, `gruvbox`, `sepia`, `high-contrast`) are CSS-custom-property blocks (`--preview-bg`/`-text`/`-link`/`-code-bg`/`-border`/`-header-border`, plus a `font-family`) applied by swapping the `markdown-body`'s class in `changeTheme()`. Because `highlight.js`'s code-highlighting CSS is a separate stylesheet, both the light and dark highlight.js themes are bundled as two inline `<style id="hljs-theme-light">` / `<style id="hljs-theme-dark">` blocks in `<head>`, and `changeTheme()` toggles which one is active by setting its `media` attribute to `'all'` vs `'not all'` (rather than swapping a `<link href>`, which only works for externally-loaded stylesheets). Which themes count as "dark" (and so need the dark hljs stylesheet) lives in one place, the `DARK_THEMES` `Set` — both `changeTheme()` and `exportAsHtml()`'s equivalent light/dark hljs pick read from it. Adding a new dark theme means adding its class name to `DARK_THEMES`, not hand-editing an `if` in two places — the two call sites used to each hardcode their own theme-name check, which is an easy way to update one and forget the other next time a dark theme is added. New theme `<option>`s go in `#themeSelector` in the same order as the CSS blocks.

### Persistence
All app state (tabs' content/name/modified-flag/image-assets/drawing-markers, active tab, theme, editor/preview visibility, sync-scroll flag, spellcheck flag, split-pane ratio, last-used template) is serialized to `localStorage` under the key `md_studio_state` via `saveStateToLocalStorage()`, called after essentially every mutating action. `fileHandle`s are not (and cannot be) persisted — reloading the page keeps tab content but loses the live file handle, so `saveCurrentFile()` on a restored tab falls through to `saveCurrentFileAs()`. Image asset data was already being stored somewhere in this JSON blob before the asset-map existed (inline in `content`); moving it to a sibling `assets` field didn't change total localStorage footprint, just where the base64 lives.

### Responsive layout (narrow viewports / phones)
A single `@media (max-width: 640px)` block near the end of the `<style>` block handles everything, reusing existing mechanisms rather than introducing a parallel mobile layout:
- The header actions, formatting toolbar, and table-controls bar switch from `flex-wrap: wrap` to `overflow-x: auto` with `flex-wrap: nowrap` — buttons become horizontally swipeable instead of wrapping into multiple tall rows.
- `<main>`'s grid switches from two columns to two **rows** (editor stacked above preview) — chosen over showing only one pane at a time by default, since the app already has editor/preview focus-mode toggles for users who want a single full-height pane; the media query just changes which axis the existing `editor-hidden`/`preview-hidden` classes collapse along (`grid-template-rows: 0 1fr` etc. instead of columns), so those toggle buttons keep working unmodified on mobile.
- The TOC panel gets a viewport-relative `max-width` instead of its fixed 260px so it can't overflow a narrow screen.
- When touching any of the header/toolbar bars, verify with `document.documentElement.scrollWidth <= window.innerWidth` that nothing leaks into page-level horizontal scroll — internal `overflow-x: auto` on a bar is fine, but the `<body>` itself gaining horizontal scroll is the classic mobile-web regression to watch for.

## Conventions to preserve

- **UI language is German** (`lang="de"`, all button labels/placeholders/confirm dialogs). Keep new user-facing strings in German for consistency.
- No external JS files, no build tooling, no package.json, no CDN dependencies — new features should be added inline in the existing `<script>`/`<style>` blocks rather than introducing a module system, bundler, or external `<script src>`, unless the user explicitly asks to restructure the project.
- The header action bar (`.actions-group`), formatting toolbar, and table controls are all icon-only now (`.icon-btn`/`.fmt-btn`/`.toolbar-btn` with an inlined SVG from `Icons/`, no visible text) with the German label/shortcut in the `title` attribute as a native tooltip — this is a deliberate style choice (chosen over a dropdown-menu-bar or icon+label layout); keep new controls in these bars consistent with it, and reuse an existing `Icons/` SVG (normalized per the Dependencies section above) rather than falling back to an emoji glyph. The search bar remains the one exception, using visible-text buttons ("Nächster"/"Ersetzen"/"Alle ersetzen") since those are full-word actions rather than single concepts an icon can represent unambiguously — don't unify it with the icon-only bars without being asked.
