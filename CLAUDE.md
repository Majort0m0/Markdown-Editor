# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This repository is a single self-contained HTML file: `Markdown-Editor.html` (~11.6MB — see Dependencies below for why). It is a client-side, no-build "Markdown Studio" editor with live preview, multi-tab documents, undo/redo, search & replace, theming, synced-scroll split view, focus modes (hide editor or preview), fullscreen mode, a table of contents panel, table row/column controls, image paste/drop, an embedded Excalidraw drawing tool, HTML/RTF export, print, responsive layout for narrow viewports, and local file save/load. There is no package manager, build step, linter, or test suite — the entire application (markup, CSS, and JS) lives in this one file.

## Running / developing

There is no build or dev server. To work on the app, open `Markdown-Editor.html` directly in a browser (double-click, or `open Markdown-Editor.html` on macOS). Reload the browser tab after every edit to see changes — there is no hot reload. The file is fully standalone (no network access required, works from `file://`) — see Dependencies below.

There are no automated tests. Verify changes manually in the browser: type in the editor pane and confirm the preview pane, toolbar buttons, and keyboard shortcuts behave as expected.

## Dependencies (bundled, not CDN)

`marked` and `highlight.js` are inlined verbatim as `<script>` blocks in `<head>` (not loaded from a CDN) so the app has zero external requests and works fully offline. If either library needs a version bump, download the new minified build and replace the corresponding inline `<script>` block's contents — do not reintroduce `<script src="https://...">` CDN tags. When editing near these blocks, be careful with tooling that matches on line content: they're ~40K–120K characters of minified code on effectively single long lines.

A third, much larger bundle — the full Excalidraw drawing app (`excalidraw.html`, a ~8.5MB standalone Vite build, custom-titled "Kritzelbuch") — is embedded the same way but **base64-encoded** rather than raw, inside `<script type="text/plain" id="excalidrawSource">`. Raw embedding wasn't viable here: unlike `marked`/`highlight.js` (pure JS, no markup), `excalidraw.html` is itself a full HTML document containing real `</script>` tags, which would prematurely close a wrapping `<script>` element. Base64 sidesteps that entirely (its alphabet contains no `<`, `>`, `/`, quotes, or backticks) at the cost of ~33% size inflation. See the "Drawing (Excalidraw)" section below for how this is decoded and used, and if this is ever rebuilt/updated, regenerate it the same way — read the new `excalidraw.html`'s raw bytes, base64-encode them, and replace only the text between the `<script id="excalidrawSource">` tags.

## Architecture

Everything is in one file with three sections: `<style>` (CSS custom properties driving both the app chrome and the swappable preview themes), static `<body>` markup for the header/toolbar/tab bar/split-pane layout, and a single `<script>` block with all application logic. There are no modules — every function is a global in that script block.

### Tab / document model
- `tabs` is the in-memory array of open documents; each tab is `{ id, name, content, fileHandle, isModified, history, historyIndex }`.
- `activeTabId` tracks the current tab. `getCurrentTab()` looks it up.
- The `<textarea id="markdownInput">` and preview `<div>` are singletons shared by all tabs — switching tabs (`switchTab()`) writes the outgoing tab's content back into the tab object before swapping in the new tab's content into the shared editor/preview elements. Any new feature that reads/writes "the current document" must go through this same save-on-switch pattern or it will leak state between tabs.
- `fileHandle` holds a File System Access API handle (when the browser supports `showSaveFilePicker`) so `saveCurrentFile()` can write back to the original file without a picker; falls back to a download-blob `<a>` click otherwise.
- `tab.isDefaultName` tracks whether a tab still has its auto-generated name (`true` for a blank "Neu" tab, `false` for anything opened from a file). While `true`, `updateTabNameFromFirstHeading()` (called from `updatePreview()`) live-renames the tab from the document's first line whenever it's a `#`–`######` heading, sanitized into a filename. `saveCurrentFileAs()` sets it back to `false` on success either way (native picker or download fallback) so a name the user actually chose is never silently overwritten again. Persisted per-tab so this doesn't reset on reload.

### Undo/redo
- Per-tab history is a plain array of full-content snapshots (`tab.history` / `tab.historyIndex`), capped at 80 entries. `recordHistory()` is debounced 400ms after typing (see the `editor.addEventListener('input', ...)` handler) so keystrokes coalesce into one snapshot; explicit actions (toolbar formatting, task-checkbox toggles, replace-all) call `recordHistory()` immediately instead.

### Formatting toolbar — toggle-aware, not just insert
`insertFormatting(type)` is deliberately not a naive "insert markdown syntax" function:
- Inline styles (bold/italic/strike/code) go through `applyInlineFormat()`, which detects whether the current selection (or the text immediately surrounding the cursor) is already wrapped in that syntax and un-wraps it instead of double-wrapping — this is what makes the toolbar buttons behave as toggles.
- Block/line-prefix styles (h1–h6/ul/ol/task/quote) operate per-line over the full selection: `prefixCleanupRegex` strips any existing prefix before applying the new one, so switching a line from `# ` to `> ` doesn't leave both prefixes stacked. Preserve this "detect current type → strip → reapply" pattern when extending formatting types, rather than blindly prepending syntax. Headings are a single `<select id="headingSelect">` (h1–h6), not six separate buttons — its `onchange` calls `insertFormatting(this.value)` then immediately resets `selectedIndex` back to the placeholder, since the select itself isn't meant to hold state (see active-format indicator below for what shows the *current* heading level).
- The Enter-key handler (in the `keydown` listener) implements smart list continuation (task/numbered/bullet) independently of `insertFormatting`, including auto-incrementing numbered lists and exiting a list when Enter is pressed on an empty list item. Keep this logic in sync if list-prefix formats change.
- `Tab`/`Shift+Tab` inside the editor are intercepted in the same `keydown` listener to indent/outdent (2 spaces) rather than moving focus out of the textarea — a collapsed cursor inserts/removes 2 spaces directly, a range selection goes through `indentLines('indent' | 'outdent')`, which is line-based like the block-prefix logic above (same toolbar buttons: ⇤/⇥).
- Every formatting insertion is empty-by-default (no "Listenpunkt"/"Zitat"/"fetter Text"-style filler): an empty selection produces just the bare syntax (`**` `**`, `> `, `[]()`, an empty `| | |` table skeleton, …) with the cursor placed where typing should start. Preserve this if extending `insertFormatting`/`applyInlineFormat` — don't reintroduce placeholder words "to show what it looks like."

### Active-format indicator
`updateFormatButtonStates()` (called from `updatePreview()` and from a `document`-level `selectionchange` listener gated on `document.activeElement === editor`) highlights which toolbar controls apply at the current cursor position: `detectBlockTypeAtLine()` reuses the same line-prefix regexes as `insertFormatting` to set the heading `<select>`'s value or toggle the ul/ol/task/quote buttons' `active` class; `detectInlineFormatsAtCursor()` scans the current line for bold/italic/strike/code spans and checks whether the cursor position falls inside a match. This is a heuristic line-local regex scan, not a real markdown parser — good enough for a toolbar hint, but don't expect it to handle pathological nesting/escaping correctly.

### Preview rendering
`updatePreview()` re-parses the entire editor content through `marked.parse()` on every input event (no incremental diffing). Task-list checkboxes in the rendered preview are made interactive by `attachTaskCheckboxListeners()`, which re-binds a `change` listener to every checkbox after each re-render; toggling one calls `toggleTaskInMarkdown()`, which finds the Nth checkbox pattern in the raw markdown via regex and flips `[ ]`/`[x]` — this only works because checkbox order in the rendered DOM matches checkbox order in the source text, so any change to list rendering must preserve that ordering guarantee.

### Custom `marked.Renderer()` (`hljsRenderer`) — code highlighting, images, task list bullets
A single `hljsRenderer` instance overrides three default methods; if `marked` is ever upgraded, re-check all three against the installed version's `Renderer.prototype` since they replicate (not just extend) marked's default behavior and rely on its exact method signatures (object-destructured args like `{ text, lang }`, not positional):
- **`code({ text, lang })`** — `marked` v5+ removed the old synchronous `highlight` callback in `marked.setOptions()`; passing it is silently ignored (no error, code blocks just render unhighlighted — this was actually broken for a while before being noticed and fixed). Calls `hljs.highlight()`/`hljs.highlightAuto()` and returns `<pre><code class="hljs ...">`.
- **`image({ href, title, text })`** — resolves `asset:ID` hrefs to the real data URI (see the image-asset-map section below); everything else passes through unchanged.
- **`listitem(item)`** — marked's default renderer never adds any class to task-list `<li>` elements, and whether the checkbox ends up a direct child of `<li>` or nested inside a `<p>` depends on whether the surrounding list is "loose" (any blank line between items in that list makes the *whole* list loose, even items with no blank line adjacent to them) — so a CSS selector like `li:has(> input[type=checkbox])` only catches the tight case. This override replicates marked's default task-checkbox logic exactly but additionally tags the `<li>` with `class="task-list-item"` regardless of looseness, which `.markdown-body li.task-list-item { list-style-type: none; }` uses to suppress the bullet (GitHub renders task items without a bullet marker; showing both a bullet *and* a checkbox reads as broken/unfamiliar). Keep the CSS rule and this renderer override in sync in both the live preview stylesheet and the `exportAsHtml()` template string.

### Editor/preview pane visibility (split view, focus modes)
`showEditor` and `showPreview` are independent booleans; `applyPaneVisibility()` is the single function that reconciles both into the `editor-hidden`/`preview-hidden` classes on `#mainContainer`, the two toggle buttons' `active` state, and the formatting toolbar's visibility. `toggleEditor()`/`togglePreview()` both guard against hiding both panes at once (auto-re-enables the other one) — any new code that flips these flags directly should go through `applyPaneVisibility()` afterward rather than touching classes ad hoc. The two-column CSS grid (`main { grid-template-columns: 1fr 1fr }`) relies on `.editor-pane`/`.preview-pane` each having an explicit `grid-column: 1`/`grid-column: 2` — without that pin, hiding the *first* grid item via `display: none` makes the browser auto-place the remaining item back into column 1 (now 0-width) instead of stretching it, collapsing it to near-zero width. Keep both `grid-column` pins if this layout is touched.

### Fullscreen mode
`toggleFullscreen()` just calls the standard `document.documentElement.requestFullscreen()` / `exitFullscreen()`. A `fullscreenchange` listener (not the button's own click handler) is what actually syncs the button's `active` class, since fullscreen can also be exited via `Esc` or browser UI outside the app's control. Note for testing: some sandboxed/automated browser contexts reject `requestFullscreen()` with `"Permissions check failed"` even though the API and `document.fullscreenEnabled` both report as available — that's an environment restriction, not a sign the code is wrong.

### Table of contents
A floating button (`#tocToggleBtn`) and panel (`#tocPanel`) positioned `position: absolute` inside `#mainContainer` (not inside `.preview-pane`) specifically so they stay put on screen while the preview scrolls underneath — `.preview-pane` is the scroll container, so anything absolutely positioned *inside* it would scroll away with the content. `updateTocPanel()` rebuilds the list from `preview.querySelectorAll('h1, h2, h3, h4, h5, h6')` (only when the panel is open — cheap to call unconditionally from `updatePreview()`) and each entry calls `headingEl.scrollIntoView()` directly rather than generating anchor IDs/slugs, since the actual heading elements are already right there in the live DOM. Closes on: entry click, outside click, `Escape` (added to the same shared listener as the other modals), and is force-hidden via CSS whenever `.preview-hidden` is active (no preview to outline).

### Table controls
A contextual bar (`#tableControls`, between the formatting toolbar and `<main>`) that only appears while the cursor sits inside a markdown table, driven by `findTableBlock()` — it locates the contiguous run of "lines containing a pipe" around the cursor and confirms the second line matches `TABLE_SEPARATOR_RE`, so a stray `|` in a sentence never gets misdetected as a table. This is a from-scratch line-based table editor operating on raw text, not the rendered DOM:
- `getCellRanges(lineText)` finds cell character ranges by locating unescaped `|` positions and adding virtual boundaries at the string ends when a row omits the leading/trailing pipe (both are valid GFM) — this is what lets column-detection work identically for `| A | B |` and bare `A | B` styles.
- Row insert/delete and column insert/delete all funnel through `commitTableEdit()`. Column operations rebuild **every** row in the block via `buildRowFromCells()` into a canonical `| a | b |` shape — this normalizes/reformats the whole table (loses any hand-aligned padding) but sidesteps a much harder problem (splicing a new cell into arbitrarily-padded existing rows). Accepted trade-off; don't try to preserve exact original spacing without a good reason to.
- Row insert/delete on the header or separator line is deliberately redirected/blocked (`cursorLine <= separatorLine` guard) — the separator **must** immediately follow the header for GFM to recognize the table at all, so "insert a row before the header" can't mean what it literally says without breaking the table; it's redirected to insert as the first body row instead. Deleting the header/separator via this UI is blocked outright.
- The bar's visibility (`updateTableControlsVisibility()`) is gated on `showEditor` in addition to cursor-in-table — it's called both reactively (`selectionchange`, `updatePreview()`) and explicitly from `applyPaneVisibility()`, because otherwise toggling the editor pane hidden wouldn't hide a bar that's logically about editing raw source you can no longer see.

### Synchronized scrolling
`syncScrollFrom('editor' | 'preview')` mirrors scroll position by percentage (`scrollTop / (scrollHeight - clientHeight)`) between the textarea and `#previewPane`. The `isSyncingScroll` flag plus a `requestAnimationFrame` reset prevents the two scroll listeners from re-triggering each other in an infinite loop — keep both the flag and the rAF-deferred reset if this is touched (a synchronous reset re-enters before the mirrored scroll event fires and recurses). Disabled automatically whenever either pane is hidden (nothing to sync against) and toggleable via `syncScrollBtn`/`syncScrollEnabled`.

### Image insertion (paste & drag-and-drop) — asset map, not inline base64
Pasted/dropped images are **not** embedded as a giant inline `data:` URI in the visible markdown source. Each tab has a `tab.assets` map (`{ img_1: 'data:image/...;base64,...', ... }` plus `tab.assetCounter`); the editor text only ever holds a short `![name](asset:img_1)` reference. This exists specifically to keep the source editable/scrollable/diffable — a multi-MB base64 line used to make the textarea (and undo history, and search) unwieldy.
- **Insert flow**: the `editor` `paste` listener and the window `drop` handler both call `requestImageInsertChoice(file)`, an async dialog (`#imageInsertModal`) that loads the image, offers "Verkleinert einfügen" (canvas-resized to `IMAGE_MAX_DIMENSION`px longest side, re-encoded as JPEG at `IMAGE_JPEG_QUALITY`, hidden if the image is already smaller) alongside "Original einfügen", and resolves a Promise with `{ dataUrl, name }` (or `null` if cancelled). `insertImageAsset(dataUrl, name)` then does the actual asset-map write + short-reference insertion. Don't reintroduce a "just insert the file directly" path that skips this dialog — that's the exact problem this system replaced.
- **Render**: `hljsRenderer.image({ href, title, text })` (the same custom `marked.Renderer()` used for syntax highlighting) resolves an `asset:ID` href to the real data URI via `getCurrentTab().assets` at render time; any other href passes through unchanged. This is why switching tabs "just works" for images — the renderer always looks at whatever tab is currently active.
- **Save / export**: `editor.value` (and therefore `tab.content`, localStorage, undo history) always contains the short `asset:` reference — never the full base64. `saveCurrentFile()`/`saveCurrentFileAs()` run the content through `inlineAssetsIntoContent(content, assets)` (regex-substitutes `asset:ID` back to the real data URI) before writing, so the saved `.md` file is still a portable, standalone document with no dependency on this app. `exportAsHtml()` doesn't need this step — it already renders through `hljsRenderer.image`, which resolves the reference at render time.
- **Opening/pasting content that already has inline base64 images** (a `.md` file saved elsewhere, or one saved by an older version of this app): `createNewTab()` runs all new tab content through `extractInlineImagesToAssets(content)`, which regex-detects `![alt](data:...;base64,...)` and converts it into the asset-map form on the way in. Any code path that sets a tab's initial content should go through `createNewTab`, not assign `tab.content` directly, or this normalization gets skipped.
- Drag-and-drop still branches on MIME type: images go through the dialog into the *current* tab's assets, everything else still opens as a new tab via `createNewTab` (the original behavior — don't collapse that branch).

### Drawing (embedded Excalidraw)
The 🖌️ "Zeichnung" toolbar button opens `#drawingModal`, whose `<iframe id="drawingFrame">` is loaded via `frame.srcdoc = getExcalidrawHtml()` (base64-decoded once, cached in `cachedExcalidrawHtml`) rather than `frame.src` pointing at a sibling file. That choice is deliberate and load-bearing: an iframe using `srcdoc` is same-origin with the embedding page **by spec, regardless of whether the parent was opened over http(s) or via `file://`**. A `src="excalidraw.html"` iframe would only reliably be same-origin over http(s) — for the "download the one file and double-click it" use case, that same-origin guarantee is what makes the rest of this section possible at all.

There is no supported API for scripting the standalone Excalidraw app from the outside (it's the full end-user app, not the `@excalidraw/excalidraw` React component library, which *does* have a clean imperative API but would mean building a whole separate app rather than reusing this file). Both directions below instead drive Excalidraw's actual UI programmatically, discovered by inspecting its DOM for stable hooks (`data-testid` attributes and element `id`s — Excalidraw's own E2E test infrastructure, far more stable across rebuilds than guessed CSS classes or coordinates) rather than by any documented contract:
- **Loading an existing drawing** (`openDrawingModal(assetId)`) polls for `canvas.excalidraw__canvas.interactive` to confirm the app has actually mounted, then simulates a native drag-and-drop of the asset's stored PNG onto that canvas via `dropFileOntoExcalidraw()`. This works because Excalidraw embeds the full editable scene inside a `tEXt` chunk of any PNG exported with "Szene einbetten" on, and *automatically* restores it when such a file is dropped onto the canvas — a real, long-standing Excalidraw feature this leans on rather than reimplements.
- **Saving** (`exportDrawingBlob()`) clicks through Excalidraw's own menu → `[data-testid="image-export-button"]` → forces `#exportEmbedSwitch` (embed scene) on and `#exportOnlySelected` off → clicks the `button[aria-label="Als PNG exportieren"]` → captures the resulting `Blob` by patching `URL.createObjectURL` **inside the iframe's own window**, not the parent's, and not by touching any Excalidraw-internal function. Forcing `#exportOnlySelected` off is not optional: it defaults to on whenever anything is or *was* selected (surviving even a subsequent deselect/Escape), and left on it silently exports only the selected shape(s) — this was an actual bug caught only by testing a two-shape drawing with the second shape left selected, not something obvious from reading the code.
- Both are inherently coupled to *today's* Kritzelbuch/Excalidraw build's DOM structure and German menu strings. If that build is ever regenerated from a newer Excalidraw version, re-verify every selector above still resolves before assuming any of this still works — none of it is a stable, versioned contract.

Saving writes the resulting data URL into `tab.assets[assetId]` exactly like a pasted image (new drawings go through the same counter-based `img_N` allocation as `insertImageAsset`), plus `tab.drawingAssetIds[assetId] = true` so it's distinguishable from a regular photo later. Editing an *existing* drawing reuses the same `assetId` rather than minting a new one — the markdown source's `![Zeichnung](asset:img_3)` reference never has to change, only the asset data it points to, so nothing downstream (undo history diffing, search, the reference itself) needs to know an edit happened at all.

In the rendered preview, `hljsRenderer.image` wraps only assets present in `tab.drawingAssetIds` in a `<span class="drawing-wrapper" data-asset-id="...">` with a hover-revealed "✏️ Bearbeiten" button; a single delegated click listener on `preview` (registered once, not re-bound per render) reopens `openDrawingModal` for whichever wrapper was clicked — clicking the image itself works too, since both are inside the same wrapper. This wrapping is suppressed during `exportAsHtml()` via the `suppressDrawingControls` flag (flipped on immediately around that one `marked.parse()` call) so a standalone exported HTML file gets a plain `<img>` instead of a button wired to a function (`openDrawingModal`) that won't exist in that file.

`tab.drawingAssetIds` is persisted the same way as `tab.assets`/`tab.assetCounter` and must stay in sync with them in every place tabs are created, saved, or restored (`createNewTab`, `saveStateToLocalStorage`, `loadStateFromLocalStorage`) — it was missed on the first pass through `saveStateToLocalStorage`/`loadStateFromLocalStorage` and silently dropped the "this is a drawing" marker on every reload until caught by testing the full persistence round-trip explicitly, not just the happy path of inserting a drawing once. Note this marker is inherently lost if a `.md` file is closed and reopened later (or opened on another machine) — `extractInlineImagesToAssets()` has no way to know from a bare `![alt](data:...)` that it originally came from Excalidraw, so it becomes a regular (non-editable-via-Excalidraw) image on reimport. Detecting this by peeking into the embedded PNG's own metadata would be possible but isn't implemented — an accepted limitation, not an oversight.

### HTML export & print
`exportAsHtml()` builds a fully standalone HTML document (inline `<style>`, inline rendered markdown) by reading the *current* theme's `--preview-*` custom properties off `getComputedStyle(preview)` rather than hardcoding each theme's colors again — if a new preview theme is added, the export picks it up automatically as long as it still defines the same `--preview-*` variable names. It also inlines whichever of `#hljs-theme-light`/`#hljs-theme-dark` is currently active so exported code blocks keep their highlighting. Printing is just `window.print()` on the toolbar's 🖨️ button plus an `@media print` block that hides everything except `.preview-pane`.

### RTF export
`exportAsRtf()` walks the **rendered `#markdownPreview` DOM** (`rtfFromNode()`, recursively) rather than re-parsing markdown or reusing marked's tokens — deliberately, since by the time content reaches that DOM, `hljsRenderer.image` has already resolved every `asset:ID` to a real data URI, so image handling needs zero extra asset-map lookups here. A few RTF-specific things worth knowing before touching this:
- `escapeRtfText()` iterates **UTF-16 code units** (`charCodeAt`), not Unicode code points — this is intentional, not an oversight: RTF's `\uN?` escape is defined per UTF-16 unit, so iterating code units means an astral character (emoji, etc.) naturally splits into the correct two-`\u` surrogate-pair sequence without any special-casing.
- Images are always re-encoded to PNG via an offscreen `<canvas>` (`imageElementToRtfPict()`) regardless of the original format, then hex-encoded (RTF `\pict` needs hex, not base64) — this guarantees `\pngblip` compatibility even for source formats RTF has no blip type for (GIF, WebP), at the cost of losing JPEG's compression for photos. Dimensions come straight off the already-loaded `<img>` element's `naturalWidth`/`naturalHeight` (no async re-fetch needed).
- Lists, tables, and task checkboxes are hand-rolled with plain indentation/prefixes (`\li<N>` + a literal `•`/`1.`/`☐`/`☑` character) rather than real RTF list-definition tables (`\pn` et al.) — those are one of the gnarliest, most reader-inconsistent parts of the RTF spec; this trades "editable numbered list in Word" for "looks right when pasted," which is what "paste into an email" actually needs.
- The whole thing is synchronous — no `await` anywhere — because every image is already decoded and sitting in the live DOM by the time export runs.

### Modals (keyboard shortcuts help, image insert dialog)
Both are the same plain pattern: a `.modal-overlay`/`.modal-card` pair, closed via a ✕ button, a click on the overlay backdrop (checked with `event.target === this` in the inline `onclick`), or the shared document-level `Escape` listener (which closes both, gated on each one's `active` class). If a third modal is added, generalize this instead of copy-pasting the overlay/backdrop-click/Escape wiring a third time.

### Word/character count
`updateStats()` writes `${words} Wörter · ${chars} Zeichen` into `#docStats` in the footer; it's called from inside `updatePreview()` (so it can't drift out of sync with the rendered content) and from `setEmptyState()` (to clear it).

### Theming
Preview themes (`theme-github-light/dark`, `solarized`, `nord`, `academic`) are CSS-custom-property blocks applied by swapping the `markdown-body`'s class in `changeTheme()`. Because `highlight.js`'s code-highlighting CSS is a separate stylesheet, both the light and dark highlight.js themes are bundled as two inline `<style id="hljs-theme-light">` / `<style id="hljs-theme-dark">` blocks in `<head>`, and `changeTheme()` toggles which one is active by setting its `media` attribute to `'all'` vs `'not all'` (rather than swapping a `<link href>`, which only works for externally-loaded stylesheets) — a new dark theme needs this same light/dark `media` toggle or code blocks will render with light-on-dark unreadable contrast.

### Persistence
All app state (tabs' content/name/modified-flag/image-assets/drawing-markers, active tab, theme, editor/preview visibility, sync-scroll flag, spellcheck flag) is serialized to `localStorage` under the key `md_studio_state` via `saveStateToLocalStorage()`, called after essentially every mutating action. `fileHandle`s are not (and cannot be) persisted — reloading the page keeps tab content but loses the live file handle, so `saveCurrentFile()` on a restored tab falls through to `saveCurrentFileAs()`. Image asset data was already being stored somewhere in this JSON blob before the asset-map existed (inline in `content`); moving it to a sibling `assets` field didn't change total localStorage footprint, just where the base64 lives.

### Responsive layout (narrow viewports / phones)
A single `@media (max-width: 640px)` block near the end of the `<style>` block handles everything, reusing existing mechanisms rather than introducing a parallel mobile layout:
- The header actions, formatting toolbar, and table-controls bar switch from `flex-wrap: wrap` to `overflow-x: auto` with `flex-wrap: nowrap` — buttons become horizontally swipeable instead of wrapping into multiple tall rows.
- `<main>`'s grid switches from two columns to two **rows** (editor stacked above preview) — chosen over showing only one pane at a time by default, since the app already has editor/preview focus-mode toggles for users who want a single full-height pane; the media query just changes which axis the existing `editor-hidden`/`preview-hidden` classes collapse along (`grid-template-rows: 0 1fr` etc. instead of columns), so those toggle buttons keep working unmodified on mobile.
- The TOC panel gets a viewport-relative `max-width` instead of its fixed 260px so it can't overflow a narrow screen.
- When touching any of the header/toolbar bars, verify with `document.documentElement.scrollWidth <= window.innerWidth` that nothing leaks into page-level horizontal scroll — internal `overflow-x: auto` on a bar is fine, but the `<body>` itself gaining horizontal scroll is the classic mobile-web regression to watch for.

## Conventions to preserve

- **UI language is German** (`lang="de"`, all button labels/placeholders/confirm dialogs). Keep new user-facing strings in German for consistency.
- No external JS files, no build tooling, no package.json, no CDN dependencies — new features should be added inline in the existing `<script>`/`<style>` blocks rather than introducing a module system, bundler, or external `<script src>`, unless the user explicitly asks to restructure the project.
- The header action bar (`.actions-group`) uses icon-only buttons (`.icon-btn`, 34×34px, no visible border, subtle hover fill) with the German label/shortcut in the `title` attribute as a native tooltip — no visible text. This is a deliberate style choice (chosen over a dropdown-menu-bar or icon+label layout); keep new header actions consistent with it. The search bar and formatting toolbar are separate, intentionally different button styles (text-labeled chips and boxed icon glyphs respectively) — don't unify them without being asked.
